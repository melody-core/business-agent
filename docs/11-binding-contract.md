# 业务绑定合同

实例之间的差异只允许出现在绑定里。架构文档不因某个业务而改写。

绑定由人确认后生效。实施 AI 可以起草，不能在未知时填上猜测。

## 必填

### 项目

- 名称、领域一句话、界面语言、时区
- Agent 仓库的名称与 Git 地址
- 提出人如何称呼这个产品（页面标题）

### 已登记仓库

每个仓库一条，字段见 [`contract/repository.schema.json`](../contract/repository.schema.json)：

- 稳定的 `key`
- 克隆地址
- 人话角色（提出人能看懂的入口名）
- `baseBranch`（以远端实际主干为准）
- 这个仓库负责什么
- 运行时种类与版本
- 构建命令与测试命令；没有测试就明确写 `tests.required: false`
- 本地开发时如何只启动这一个服务，包括端口
- 是否允许自动改码；默认允许的路径前缀

仓库数量不限。只有一个仓库时，K8 仍然要求显式指定它。

### 保护分支

列出任何 Agent 不得直接推送的分支。至少包含各仓 `baseBranch`，以及绑定中出现的共享环境分支。

### 发布环境

每个环境：名称、目标分支、是交接还是允许确认后推送、给人看的地址（可空）。生产默认 `mode: handoff`。

### 角色

谁是 requester、operator、admin。P0 若只有一个访问口令，写明口令持有者默认角色，以及发布是否仍要二次确认。

### 模型

- 一个兼容 Chat Completions 的基地址，放在环境变量里
- 路由或对话模型名、编码模型名，可以相同也可以分开
- 密钥的环境变量名

不在蓝图或实例文档中写死供应商。供应商专有参数只有在该实例验证过协议差异后才写入绑定，并注明只作用于哪个模型名。

### 领域文档

实例必须有，且开工前阅读：

- `docs/domain-overview.md`：业务是什么、谁使用、主要对象、不做什么
- `docs/change-map.md`：哪类需求会落到哪个仓库
- `docs/repositories/<key>.md`：该仓的入口、目录、运行时、测试方法、已知边界

这些文档从仓库和人的说明起草，经人确认。Agent 在影响面判断时引用它们，不临时发明仓库职责。

## 选填

| 项 | 缺省 |
| --- | --- |
| 预览源 | 空。页面不猜测地址 |
| 只读证据源 | 关闭 |
| 统一登录反代 | 不接。使用访问口令 |
| 自动开始队列 | 关闭。收口后询问是否开始下一条 |
| 自动编码 | 关闭，直到实施计划确认路径已经测过 |
| 对齐审查 | 开启 |
| 浅克隆深度 | 1。checkout 时仍 fetch 主干最新提交 |
| 风险归档 | 关闭 |

## 外部阻塞类别

列出该业务里 Agent 解决不了、必须找人的条件。典型项是账号、权限、私有依赖凭证、网络策略。不要把某家公司的平台名称写进架构；写进该实例的阻塞说明即可。

## 禁止写入绑定的内容

- 密钥的值
- 把未登记系统假装成可改仓库
- 用「全部仓库」代替允许列表
- 用一条通用 Shell 代替各仓验证命令
- 把生产环境设为无需确认的自动推送

## 示例

[`examples/bookstore/`](../examples/bookstore/README.md) 是虚构绑定，用来对照字段。实施时整份替换成目标业务的事实，不保留示例里的仓库和规则。

## 变更

增减仓库、修改验证命令、修改保护分支或模型协议，都是 Agent 仓库的一次变更。正在进行的迭代若依赖旧绑定，按版本失效处理，不沿用旧确认去改新范围。

# 上下游对齐

本闸门防止「上游已确认，下游悄悄改了规则」。版本确认不等于语义正确。每个待确认产物在进入确认卡之前，经过一次与写作者分开的审查。

审查可能漏判。它不承诺零缺陷，也不代替已配置的验证和业务验收。

## 规则从哪里来

- 已确认需求的目标、范围、验收项生成稳定编号。
- 产品方案里显式写出的规则逐条保留，不能被摘要漏掉。
- 审查还可以抽取带原文依据的持续约束。编号来自原文的稳定哈希。
- 「当时还没实现」不是永久约束。

后续阶段核对需求、产品规则和全部前序正文。下游的普通批准不能覆盖上游规则。要改规则，回到「调整需求」，重新确认；此后旧版本失效。

局部一致不等于整条链路一致。审查要看范围、字段、异常与降级、声明为不变的行为，以及最终结果。作者写「已对齐」不算通过。

## 谁来审

使用与写作者分开的一次模型调用。审查者不获得改码权限，不新增外部写入能力。

- 设计阶段：要求方案合理，并写明将如何验证。不要求代码已经存在。
- 交付阶段：核对已批准的文件清单、实际差异，以及工作台记录的构建和测试证据。

审查输入带行号。模型引用候选条款、对应的上游条款和实际证据。服务端回填原文。错来源、重复或缺失编号、越界引用、伪造引用都不能通过。

`passed` 由服务端计算。模型自报的通过无效。

## 状态

| 状态 | 含义 |
| --- | --- |
| passed | 这一次独立检查通过 |
| blocked | 发现冲突或缺项 |
| failed | 检查没有完成（模型故障、格式不合格、超时） |
| missing | 还没有检查 |
| stale | 绑定的版本已经变化 |

产物生成合格之后才创建待确认。直接调用确认命令也要核对对齐状态。模型故障、格式不合格或超时不放行。

输入超过预算或规则条数超过上限时，拒绝审查，禁止截断后给通过。默认预算：完整输入 350,000 字符，规则 100 条。单次审查最多两次结构化重试。

设计文档发现冲突时，最多自动修正 **当前文档** 两次，不改上游。同一冲突重复出现则停止，保留草稿，不创建确认。实施方案被阻断时保留草稿，人可以重试。交付审查不通过时，实现者只能在原批准范围内修正并复验，自动继续仍受开发阶段的轮次上限约束。

## 指纹

报告绑定：策略版本、需求版本、全部上游正文、当前产物。交付还绑定源码、实施方案和实际验证证据。

任一相关变化都使原结果过期。写入前再次核对版本和运行凭证。停止或并发修改不能把结果记入旧批准。

每次结果追加到不可覆盖的历史。页面展示当前版本的原文、冲突、缺项和失效原因。历史方案不借用当前版本的报告充当当时的证据。

## 开关

对齐默认开启。它只作用于已有已确认需求、且仍在处理的迭代。已完成、已放弃，以及没有需求卡的旧流程不追溯改写。

管理员可以显式关闭。关闭后页面标成未启用，不伪造通过。普通批准不能豁免此闸门。另行存在的风险归档是独立的人工授权，不会被本闸门自动触发，也不能反过来扩大写入范围。

## 实例要求

实现对齐时提供：

- 写作者与审查者分开的调用
- 服务端计算的状态
- 版本指纹与失效
- 不可覆盖的历史
- 确认命令和交付命令对此状态的硬检查

不要求实例绑定某一种模型供应商。审查模型与写作模型一样，只通过绑定里的兼容接口配置。

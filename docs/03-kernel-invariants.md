# 内核不变量

任何通道、任何模型、任何运行时都满足下表。违反时命令失败并留下证据。不允许「警告后继续」。

| ID | 不变量 | 失败时 |
| --- | --- | --- |
| K1 | 全局至多一条 `working` 或 `blocked` 迭代 | `new-iteration` 拒绝，并打印当前 id、标题、状态、阶段、最近活动时间，以及如何 `complete`、`abandon` 或继续当前任务 |
| K2 | 业务改动从该仓 **刚 fetch 的** `origin/<baseBranch>` 创建新功能分支 | 仓库缺失、符号链接、fetch 失败、本地已有同名分支，均失败。不得复用旧需求分支 |
| K3 | 脏工作区不得切分支，也不得据此开一条需要切分支的新迭代 | 列出 `git status`，等待人处理 |
| K4 | 业务提交只发生在 `target-repos/<key>` 自身的 Git 历史 | Agent 仓库拒绝暂存 `target-repos/` |
| K5 | 已登记仓库必须是独立 clone | `check` 发现符号链接即失败 |
| K6 | 不把密钥写入档案、日志、页面和模型可见上下文 | 命中密钥材料则拒绝落盘，并只记录事件类型 |
| K7 | 配置为必须确认的阶段，没有 Kernel 回执不得进入下游 | 模型、聊天里的「好的」都不算数。编排器要把决定写成回执 |
| K8 | `dev` 必须指定一个已登记仓库，并且当前分支是本期 `feat/<id>` | 缺仓库、多仓库、分支不符，都拒绝。一次只启动一个服务 |
| K9 | 保护分支只有 `publish` 且带已验证的人工确认才能推送 | 其他 push 拒绝。默认发布只写交接计划 |
| K10 | 编码运行时与人不得同时可写同一仓库 | 锁的持有者是 host 或 human。心跳过期只告警，不自动抢锁 |

`--allow-active-iteration` 只允许出现在只读的 `check` 排障。它不能搭配 `new-iteration`。

## K1 的附加规则

拒绝信息里要有可执行的下一步，不能只说「忙」。

- 新消息属于当前任务：追加为追问或调整，不另开任务。
- 新消息是另一条需求：写入队列，不执行。
- 维护、巡检、未部署、未授权的旧候选，都不构成重开已收口任务的理由。
- 为了腾出通道，不得把未验收的业务工作标成完成。可以 `abandon` 结束占位，并写明成果保留、不代表验收或发布。
- 通道来源不代表任务类型。系统占用和用户待办分开统计。队列计数只包含当前身份可见且已确认的项。

`set-active` 切到另一条 `working` 迭代视为抢锁，仅 admin，并写入活动记录。

## K2 的算法

对每个需要改动的仓库：

1. 路径不存在，或是符号链接：失败。
2. `git status --porcelain` 非空：失败，并列出文件。
3. `git fetch origin <baseBranch>`。浅克隆只要求这条主干是新的；需要完整历史时再单独加深。
4. 读取 `origin/<baseBranch>` 的提交号。
5. 分支名为 `feat/<iteration-id>`，除非人显式指定且仍从该提交创建。
6. 本地或远端已有同名分支：失败。
7. `git checkout -b <branch> <sha>`。
8. 把主干名和提交号写入迭代元数据与活动记录。

主干名只来自该仓库配置的 `baseBranch`。配置缺失时，才读取远端 HEAD 的符号引用。禁止写死某一个全局主干名。

若业务另有变更单系统，它是可选后置：跟踪已经创建的功能分支。Agent 不等待外部系统先开分支。

## K7 的回执

```
confirmation_id
iteration_id
stage
artifact_version
summary
decision: approve | reject | comment
actor_role
created_at
```

超时不自动批准，任务记为 `blocked`。下游命令在执行前重新读取回执，并核对产物版本仍是当时批准的那一版。

口头确认要由编排器调用 `confirm` 落盘。只在对话里复述「用户已同意」不会放行。

## K8 与 K9

`dev` 的空仓库列表是失败，不是「启动全部」。跨多个仓库的需求共用一个迭代 id，各仓各自有 `feat/<id>`，但服务仍一次起一个。

保护分支名单来自绑定，而不是写死在代码里。名单至少覆盖该业务的主干和已声明的共享环境分支。`publish` 不带确认时只生成计划：目标环境、仓库、提交、尚未执行的动作。确认必须来自 operator 或 admin 的通道身份，模型不能自签。

## 检查与修复的边界

`check` 区分两层：

- workspace：Agent 仓库自身的命令、模板、规则、运行时可执行。
- business：已登记仓库都在、是独立 clone、领域文档与配置一致、该仓声明的运行时和依赖满足开工条件。

默认为两者一起。可自动修复的项交给 `init`：目录、依赖安装、按绑定拉取缺失的 clone。最多有限轮次。

只有权限、账号、网络策略、私有依赖凭证这类外部条件才升级给人。`init` 不申请权限，不改写全局 Git 身份，不执行破坏性清理。

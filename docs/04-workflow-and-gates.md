# 工作流与闸门

## 入口是对话

提出人先和 AI 说话。问候、咨询、讨论实现思路不创建迭代，也不入队。咨询对话单独保存，不占 K1。

AI 根据当前对话整理：

- 目标
- 范围内与范围外
- 可测试的验收标准
- 可能影响的已登记仓库
- 是否改变用户可见路径

确有关键缺口才追问。不要求提出人选择模型、运行模式或内部仓库编号。已经写在已确认文档、现有界面或源码里的事实，不重复追问。

可执行需求必须先展示完整需求卡。提出人确认的是 **当前版本**。确认后写入一条持久化队列项。空闲时开始；忙碌时说明占用类型和下一步，不编造等待时长。

已有排队项不删除、不自动确认。可以打开全文，也可以拉回对话里修改，再确认并更新 **同一条** 队列项。重复提交幂等。

已启动的任务若要改需求：停止正在进行的设计或开发，回到对话澄清，再次确认时更新同一任务。确认绑定原需求指纹；确认期间出现的新版本被拒绝覆盖。旧阶段产物和已做改动都保留，旧的设计与实施授权全部失效，从产品方案重新走。开发只使用最新确认的需求快照。

## 阶段

```
对话
  → 确认当前版本需求卡
  → 排队；K1 空闲才开始
  → check；失败则 init 或记录外部阻塞
  → 判断影响仓库
  → 需要改已登记仓库时 checkout-from-base
  → 产品方案 [确认]
  → 界面方案 [确认]（需求明确不涉及用户可见变化则跳过并写明原因）
  → 技术方案 [确认]
  → 测试与验收用例 [确认]
  → 文件级实施方案 [确认]
  → 开发（执行器就绪且授权仍有效）
  → 已配置的验证
  → 业务验收
  → 本地交付提交
  → 发布交接 [确认后才可能推送]
  → complete，释放锁
```

只改 Agent 仓库的文档、命令或做纯调研时，跳过 checkout。跳过也要写入活动记录。

| 阶段 | 产物 | 确认 | 何时需要 |
| --- | --- | --- | --- |
| check | `health-check.md` | 否 | 始终 |
| init | 初始化报告 | 仅当需要人工处理 | check 有可修复项或外部阻塞 |
| checkout | `pre-iteration.md` | 否 | 要改已登记仓库 |
| 产品方案 | `product-design.md` | 是 | 始终 |
| 界面方案 | `ux-design.md` | 是 | 用户可见路径变化 |
| 技术方案 | `technical-design.md` | 是 | 代码或系统行为变化 |
| 用例 | 用例文档 | 是 | 始终 |
| 实施方案 | `implementation-plan.md` | 是 | 要改代码 |
| 开发 | 功能分支上的提交 | 否，但依赖上游确认 | 实施方案已确认且执行器就绪 |
| 测试 | `test-report.md` | 否 | 始终留下结果 |
| 验收 | 逐项验收记录 | 是 | 交付前 |
| 发布 | `publish-report.md` | 是 | 提出人要求发布时 |

阶段状态由服务端的产物和回执计算。对话文案不能把阶段标成已完成。

## 每个阶段的协议

1. 在 `activity.md` 记录阶段开始。
2. 读取需求快照和全部前序产物，不只读上一阶段的摘要。
3. 只生成本阶段该写的内容。篇幅随改动规模收敛。前序结论引用，不整篇复制。
4. 按配置决定是否创建确认卡。
5. 记录产物路径、版本、结果和下一步。

技术方案必须引用实际读过的源码位置与版本。没有读到的行为写成未知，不补造。

用例至少覆盖主路径，以及权限不足、非法状态、空数据和配置未生效。每条验收标准至少对应一个用例。页面类需求写端到端用例；纯接口或纯数据处理写相应的接口或作业用例，不为了凑格式伪造页面。

文件级实施方案列出：

- 允许修改的仓库与路径，以及每处意图
- 明确不改的路径
- 将使用的验证命令（来自配置，不由模型现编）
- 与验收条目的对应关系

依赖清单、构建配置、密钥和发布清单默认不在自动写入范围内，除非实施方案把它们逐项列出并获得确认。

## 版本失效

下列任一变化都使下游授权失效：

- 需求卡版本变化
- 已确认的前序产物被替换
- 实施方案的文件清单或哈希变化
- 验证命令或验证策略变化
- 源码相对已确认基线发生变化

失效后保留旧全文和旧回执，供审计。新版本重新确认。读取历史不会恢复旧批准。

已确认但尚未启动的需求可以撤回并调整。原文保留，旧确认失效，再次确认前不执行。撤回和启动放在同一个 Kernel 事务里，重复请求和重启可以恢复。

## 执行器开关

设计文档的生成不依赖自动编码开关。开关关闭时，界面显示设计可以继续、开发等待研发接管，不伪装成正在改代码。

开关打开也只表示：实施计划确认后，编码运行时 **可以** 在 Kernel 校验通过时修改允许的文件。它不授权主动修改业务仓，不授权发布，也不跳过逐次的版本、分支和路径校验。

执行器未就绪时，停在明确的等待接管，不进入开发。

## 失败

| 情况 | 处理 |
| --- | --- |
| 代码或验证失败 | 回到开发。尚未交付时，同一版本最多自动再尝试有限轮次（默认 2）。相同源码、相同失败则停止 |
| 外部权限、网络、凭证、依赖源 | 记为外部阻塞，状态 `blocked`，不空转 |
| 模型超时或断线 | 不改 Git。活动记录写失败的这一轮。已收到的证据保留 |
| 模型声称已确认 | 编排器核对回执，没有则阻断 |
| fetch 失败 | `blocked`，保留迭代 |
| Host 重启 | 读锁和档案恢复。业务服务不自动拉起，需要再次 `dev` |
| 队列启动失败 | 展示安全原因、时间、故障编号和处理方。退避重试有上限。K1 占用不是故障 |

## 活动记录

每个阶段的开始和结束都写入 `activity.md`。机器状态以元数据和 `runtime/events.jsonl` 为准；活动记录给人读，也给恢复时的 Agent 读。
